# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Critical: Next.js version

This repo runs **Next.js 16.2.3** with React 19. APIs, conventions, and file structure may differ from older Next.js versions in your training data. **Before writing or modifying anything in `app/` or `next.config.ts`, read the relevant guide in `node_modules/next/dist/docs/` (start at `01-app/` or `index.md`) and heed deprecation notices.** The project uses the App Router exclusively.

## Common commands

Package manager: **pnpm** (workspace declared in `pnpm-workspace.yaml`).

```bash
pnpm dev      # next dev — local server on http://localhost:3000
pnpm build    # next build
pnpm start    # next start (after build)
pnpm lint     # eslint via eslint-config-next (flat config in eslint.config.mjs)
```

## Architecture

Solens is a single Next.js app that exposes the same Solana-AI assistant through two front-ends:

1. **Web chat UI** — `app/page.tsx` → `app/components/{Sidebar,ChatArea}.tsx`. Privy (`app/providers.tsx`) handles login + wallet connection in the browser.
2. **Telegram bot** — `app/api/telegram/webhook/route.ts` receives Telegram updates and forwards them to the same `/api/chat` endpoint over an internal HTTP call (`INTERNAL_API_BASE_URL`, defaults to `http://127.0.0.1:${PORT||3000}`).

Both surfaces share `POST /api/chat`, which is the brain of the system.

### `/api/chat` request/response protocol

`app/api/chat/route.ts` runs an OpenAI tool-calling loop (`OPENAI_MODEL`, default `gpt-4o-mini`). Every external integration is exposed as a function tool registered in the `tools` array; the matching handler lives in the `switch (toolCall.function.name)` block in the same file.

Request body shape (consumed by both UIs):
- `message`, `history`, `walletAddress`
- `txSignerWalletAddress` — when set (e.g. Telegram custodial), transfers/swaps are built for *this* wallet as fee-payer/taker, while balances and portfolio still reference `walletAddress`.
- `chatChannel: "telegram"` and `telegramSigningMode: "privy_server" | "custodial" | "none"` — these mutate the system prompt so the assistant tells users to "tap **Confirm** in Telegram" vs. "open the web app".

Response shape:
- `message` — assistant text.
- `action?` — a discriminated union `{ type: "swap" | "transfer" | "addLiquidity" | "removeLiquidity" | "launchToken" | "claimFees" | "predictionOrder" | "sellPrediction" | "claimPrediction" | "buyNFT" | "listNFT", transaction(s): base64, ...meta }`. Tool handlers set `pendingAction` when they prepare an unsigned transaction; the front-ends are responsible for collecting a signature and broadcasting via the matching execute endpoint.
- `quickReplies?` — generated by `generateQuickReplies()` from `toolResults` only when there's no pending action.

### Two-phase on-chain pattern

Every on-chain action follows the same shape: build → sign → broadcast. The chat route only ever returns an unsigned base64 transaction inside `action`. Signing happens client-side (Privy/Phantom in the browser, server-side helpers for Telegram). Broadcast is delegated to a dedicated route per integration — they exist as separate routes because their `sendRawTransaction` settings differ:

| Action | Build (in `/api/chat` tool) | Broadcast |
| --- | --- | --- |
| Jupiter swap | `getSwapOrder` → `app/lib/jupiter.ts` | `POST /api/swap/execute` (Jupiter `/swap/v2/execute`) |
| Transfer / Meteora / Bags / Magic Eden | inline in tool handler | `POST /api/meteora/execute` (`skipPreflight: false`, polls confirmation) |
| Prediction markets (Jupiter) | `app/lib/prediction.ts` | `POST /api/prediction/execute` (**`skipPreflight: true, maxRetries: 0`** — required by Jupiter docs; do not unify with the meteora endpoint) |

`POST /api/swap/order` exists as a thin wrapper that lets the web UI request a fresh swap quote outside the chat loop.

### Solana RPC

- Server-side libraries in `app/lib/*` create connections directly with `SOLANA_RPC_URL`.
- The browser does **not** get the RPC URL. `app/providers.tsx` points Privy at `/api/solana/rpc`, which is a method-allowlisted proxy in `app/api/solana/rpc/route.ts` (see `ALLOWED_RPC_METHODS`). Add a method to that set if a new browser flow needs it; don't bypass the proxy.

### Telegram flow

Three optional signing paths, selected at runtime in `app/api/telegram/webhook/route.ts`:

1. **Privy server signing** (`privy_server`) — preferred. Requires `PRIVY_APP_SECRET` server-side and a Privy *identity token* captured during the link flow (`app/telegram/link/page.tsx` → `POST /api/telegram/link/confirm`). Stored in-memory by chat ID in `app/lib/telegram-privy-token.ts`. Signing is performed via `app/lib/privy-server-wallet.ts` against the user's embedded Solana wallet.
2. **Custodial** (`custodial`) — `TELEGRAM_CUSTODIAL_WALLETS=true` + `TELEGRAM_CUSTODIAL_MASTER_KEY`. Per-chat keypairs are AES-GCM-encrypted in `app/lib/telegram-custodial-wallet.ts` and held in memory only — restarting the process loses them. By default this only auto-executes transfer actions (`TELEGRAM_CUSTODIAL_TRANSFERS_ONLY=true`); other transactions still need the web app.
3. **None** (`none`) — webhook tells the user to open the web app to sign.

Webhook execution dispatch lives in `app/lib/telegram-transfer-exec.ts`; it signs and POSTs to `/api/meteora/execute` to broadcast.

All Telegram session state (chat history, link tokens, bound wallets, pending confirm payloads, custodial keys, Privy identity tokens) is **in-memory `Map`s, scoped per process**. Anything that needs to survive restart or scale horizontally must be added to a real store; do not assume durability.

The Telegram link token HMAC is signed with `TELEGRAM_LINK_SECRET` (or `TELEGRAM_LINK_SECRETS` for rotation). If neither is set, an in-memory random secret is generated and a warning is logged — fine for dev, breaks across restarts in prod.

### Path aliases

`tsconfig.json` maps `@/*` → repo root, so server code imports look like `@/app/lib/jupiter`. Keep new modules under `app/lib/` and import via `@/app/lib/...`.

## Environment variables

The full list lives in `README.md`; the non-obvious ones for development:

- `SOLANA_RPC_URL` — required server-side for everything Solana. The browser never sees it.
- `OPENAI_API_KEY`, optional `OPENAI_MODEL` (default `gpt-4o-mini`), optional `OPENAI_BASE_URL`.
- `JUPITER_API_KEY` — used by both `app/lib/jupiter.ts` (swaps) and `app/lib/prediction.ts` (prediction markets).
- `MAGIC_EDEN_API_KEY`, `BAGS_API_KEY` — required for the respective tools; routes throw with a setup message if missing.
- `NEXT_PUBLIC_PRIVY_APP_ID` (browser) + `PRIVY_APP_SECRET` (server) — server secret is required for Telegram → Privy server signing.
- `INTERNAL_API_BASE_URL` — set this if the Telegram webhook can't reach itself at `127.0.0.1:$PORT` (e.g. behind a reverse proxy on a different port).

`next.config.ts` whitelists `terminal.solens.app` as a dev origin — update this if developing under a different public host. (`solens.app` is retired; it 308-redirects to `terminal.solens.app`.)
